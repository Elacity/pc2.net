## TL;DR

The Chipotle `usageKey` is currently served unauthenticated to anyone who hits
`https://<supernode>/api/ddrm/provision`. This task replaces that bootstrap
shape with a **supernode-side relayer**: PC2 nodes never see the usageKey;
they instead POST Lit Action requests to the supernode, which adds the key
server-side and forwards to `https://api.chipotle.litprotocol.com`. New PC2
nodes authenticate with a one-time SIWE-style signature from their existing
wallet — no pre-shared secret, no chicken-and-egg.

**Independent of this task, the current usageKey must be rotated TODAY** since
it has been world-readable for ~6 days. Rotation procedure lives in
`.cursor/tasks/SEC-2026-04-28-WAVE8-CHIPOTLE-HARDENING/ROTATION_RUNBOOK.md`.
This task is the structural fix so a future leak cannot happen.

## Description

Eliminate the `usageKey` exposure on `/api/ddrm/provision` by inverting the
trust direction:

- **Today (v1.2.7.x)**: PC2 node → supernode (`GET /api/ddrm/provision`) →
  receives `{usageKey, apiUrl, pkpId, …}` → uses `usageKey` directly to call
  `https://api.chipotle.litprotocol.com/core/v1/lit_action`.
- **After this task (v1.2.8.0)**: PC2 node → supernode
  (`POST /api/ddrm/lit-action` with SIWE-authed body) → supernode injects
  `usageKey` server-side → forwards to Chipotle → response back to PC2.

The usageKey **never leaves the supernode disk**. Drive-by scrapers get HTTP
401. Compromised PC2 nodes can be revoked individually by wallet address.
Rotation is just `systemctl restart` after editing `ddrm-config.json` on each
supernode — no PC2 redeploy required.

### Why we got here

When a fresh PC2 node spins up (think: launcher install on a brand-new MacBook)
it has zero pre-shared credentials. The Wave 8 design picked the simplest
shape that worked end-to-end: any node can hit the supernode and get the
shared usageKey. It was a deliberate tradeoff for shipping speed against the
v1.2.0 deadline.

The Wave 8 H-01.2 hardening added an Ed25519 signature on the envelope so a
hostile supernode operator can't forge config (integrity) — but the entire
signed payload, sig and all, is still publicly downloadable (no
confidentiality).

### Threat model

| Capability granted by leaked usageKey | Severity |
|---|---|
| Execute Lit Actions in Elacity's Chipotle group (consume our quota, see what KIDs we touch via logs) | Med (scoped to allowlisted action CIDs + our PKP) |
| Access Chipotle dashboard per Irzhy | High (visibility into usage stats; possibly write actions; needs Chipotle confirmation of dashboard scope) |
| Rotation cost if we discover compromise | Low after this task ships (supernode-only); High today (entire fleet must re-provision) |

The usageKey is **shared across every PC2 node on Earth**. Compromise of any
single node — or of our supernode — exposes the same key. After this task,
each PC2 node authenticates with its own wallet signature and can be revoked
individually without touching the rest of the fleet.

## Architecture

### Wire shape after v1.2.8.0

```
┌──────────────────┐                                ┌──────────────────────────┐
│   PC2 Node       │                                │  Supernode (gateway)     │
│   (any user)     │                                │  /etc/pc2/ddrm-config    │
│                  │   1. POST /api/ddrm/auth-      │  ── usageKey lives here  │
│  ┌────────────┐  │      challenge                 │     (mode 0600, root)    │
│  │  Wallet    │──┼──→  {wallet, address}          │                          │
│  │  (EOA/SA)  │  │  ←── {nonce, expires}          │                          │
│  └────────────┘  │                                │                          │
│        │         │   2. sign nonce                │                          │
│        ▼         │      (personal_sign)           │                          │
│  ┌────────────┐  │                                │                          │
│  │ chipotle-  │  │   3. POST /api/ddrm/lit-action │                          │
│  │ client.ts  │──┼──→  Headers:                   │                          │
│  └────────────┘  │      X-PC2-Wallet: 0x…         │                          │
│                  │      X-PC2-Sig:    0x…         │                          │
│                  │      X-PC2-Nonce:  abc…        │                          │
│                  │      Body: {code, js_params}   │                          │
│                  │                                │   ┌──────────────────┐   │
│                  │                                │   │  verifySig()     │   │
│                  │                                │   │  rateLimit()     │   │
│                  │                                │   │  inject usageKey │   │
│                  │                                │   └──────┬───────────┘   │
│                  │                                │          ▼               │
│                  │                                │   ┌──────────────────┐   │
│                  │                                │   │ POST Chipotle    │───┼─→ api.chipotle…
│                  │                                │   │ X-Api-Key: <key> │   │
│                  │                                │   └──────────────────┘   │
│                  │                                │          ▼               │
│                  │  ←── {response, logs, has_err} │                          │
└──────────────────┘                                └──────────────────────────┘
```

### Three things change

1. **Gateway gets a new endpoint** — `POST /api/ddrm/lit-action` plus a
   nonce-issuing companion `POST /api/ddrm/auth-challenge`. The relayer is
   thin: SIWE-verify, rate-limit, inject `X-Api-Key`, proxy to Chipotle,
   return response.
2. **`pc2-node/src/api/chipotle-client.ts` gets a new resolution tier** —
   "Tier 0: relayer". Try the relayer first; if it answers (200 or
   well-formed 4xx), use it. Fall through to current Tier 1–4 only if no
   reachable relayer (preserves dev-mode `LIT_CHIPOTLE_USAGE_KEY` and the
   self-sovereign user-key path).
3. **`/api/ddrm/provision` gets demoted to a "config metadata" endpoint** —
   it still returns `apiUrl`, `pkpId`, `authority`, `chain`, `chainId`,
   `rpc`, `actions` (everything PC2 needs to *construct* a Lit Action) but
   the `usageKey` field is removed entirely. Fresh nodes still bootstrap
   from this endpoint without auth — but the only thing it leaks now is the
   public shape of our Lit Action setup, which is already public on
   Chipotle's group allowlist.

### Why SIWE for PC2-to-supernode auth

PC2 nodes already have wallets — both an EOA (managed via Particle / WC) and
typically a Smart Account. We already do SIWE for `userLogin` against the
Elacity GraphQL backend (see `pc2-node/data/test-apps/elacity-market/wallet.js`
function `siweLogin`). Reusing that pattern:

- Zero net-new cryptography for users to set up
- Zero pre-shared secrets between fleet and supernodes
- New nodes work the moment a wallet exists (which is "first launch of any
  Elacity dApp" today)
- Per-wallet rate limiting falls out for free
- Compromised individual wallets revocable on the supernode without affecting
  anyone else

### What this does *not* fix

This task does **not** add per-PKP scoping inside Chipotle itself. If
Chipotle supports issuing per-API-key sub-keys scoped to specific PKPs /
action allowlists / origin domains, that's a strictly stronger fix and
should be a separate v1.3 task. **Open question for Irzhy below.**

## Implementation Plan

### Phase 1 — Gateway relayer (`deploy/web-gateway/index.js`)

- [ ] Add `POST /api/ddrm/auth-challenge`:
  - Accepts `{wallet: '0x…'}` (lowercased EVM address)
  - Generates 24-byte cryptographically random nonce, base64-encoded
  - Stores `{nonce, wallet, issuedAt}` in an in-memory LRU keyed by nonce
    (TTL 120s, max 10 000 entries)
  - Returns `{nonce, expiresAt, statement: 'PC2 → Chipotle relayer auth'}`
  - Per-IP rate limit: 30 challenges/minute (`Retry-After` header on excess)
- [ ] Add `POST /api/ddrm/lit-action`:
  - Required headers: `X-PC2-Wallet`, `X-PC2-Sig`, `X-PC2-Nonce`
  - Reconstruct SIWE-equivalent message:
    `"PC2 → Chipotle relayer auth\nwallet: 0x…\nnonce: <b64>\nissuedAt: <unix>"`
  - `recoverAddress(hash(message), sig).toLowerCase() === wallet` ?
  - Consume nonce (single-use, error 401 on replay)
  - **Wallet allowlist policy** (configurable):
    - Mode A (open): any wallet that signed correctly is allowed. Useful for
      public Elacity fleet bootstrap.
    - Mode B (allowlisted): only wallets in
      `/etc/pc2/relayer-wallets.allow` (one address per line) are accepted.
      Useful if we want to limit relayer to known operator nodes.
    - Default: Mode A with rate-limiting, since the Lit Action call itself
      is scoped (action CID + PKP) and abuse is bounded by Chipotle quota.
  - Per-wallet token bucket: 100 Lit Actions/hour, refill 1/36s. Excess →
    429 with `Retry-After`.
  - Per-IP secondary bucket: 600 Lit Actions/hour (anti-distributed-abuse).
  - Body forwarded as-is to `${apiUrl}/core/v1/lit_action` with
    `X-Api-Key: ${ddrm-config.usageKey}` injected server-side.
  - Response body proxied verbatim. On Chipotle error (4xx/5xx), surface
    status + body to caller (don't swallow — PC2 needs the error semantics).
  - Audit log line per call:
    `[relayer] wallet=0x… ip=… action_chars=… status=… elapsed_ms=…`
- [ ] **Demote `GET /api/ddrm/provision`**: drop `usageKey` from the
  returned payload. Bump envelope `v: 1 → v: 2`. Old PC2 clients
  (v1.2.7.x and earlier) will see a missing `usageKey` and fail provision —
  see Phase 4 backward-compat plan below.

### Phase 2 — PC2 client (`pc2-node/src/api/chipotle-client.ts`)

- [ ] Add `RELAYER_PROVISION_URLS` constant alongside the existing
  `SUPERNODE_PROVISION_URLS`. Same two hosts, different paths.
- [ ] Add `RelayerSession` type holding `{nonce, expiresAt, lastWallet}`
  cached in-memory (no disk persistence; nonces are short-lived).
- [ ] Add `executeLitActionViaRelayer(params, walletSigner)` that:
  - Issues challenge → signs → POSTs the call
  - On 401 retry once with a fresh challenge (handles nonce-clock skew)
  - On 503 (relayer cannot reach Chipotle) returns null so caller can fall
    through to direct Tier 1-4
- [ ] Modify `executeLitAction()` resolution order to put relayer at Tier 0:

  ```
  Tier 0: Relayer (POST /api/ddrm/lit-action via supernode) ← NEW DEFAULT
  Tier 1: Explicit env LIT_CHIPOTLE_USAGE_KEY            (dev/operator)
  Tier 2: User key from Settings UI                      (self-sovereign)
  Tier 3: Cached usageKey from old provision blob        (legacy fallback)
  Tier 4: Fresh provision GET (v2 envelope = no usageKey, will fail)
  ```

- [ ] Wallet signer interface: chipotle-client must be able to sign a SIWE
  message without dragging the whole wallet stack in. Inject a
  `RelayerSigner` interface from the runtime layer:

  ```typescript
  interface RelayerSigner {
    address: () => Promise<`0x${string}`>;
    signMessage: (message: string) => Promise<`0x${string}`>;
  }
  ```

  Implementation lives in `pc2-node/src/runtime/relayer-signer.ts` and wires
  into the existing wallet helper used for SIWE login. Falls back to
  generating an ephemeral random keypair on disk if no user wallet is
  configured (rotated weekly; signed by the same SIWE handshake).

### Phase 3 — Supernode allowlist & monitoring

- [ ] Add `/etc/pc2/relayer-wallets.allow` to both supernodes (empty file =
  Mode A open, with rate limits)
- [ ] Add structured audit log to `journalctl` (already on systemd) so we
  can `grep -E '\[relayer\]' /var/log/pc2-gateway.log | jq`
- [ ] Add `/api/ddrm/relayer/health` returning
  `{relayer: 'up', chipotle_reachable: bool, key_loaded: bool}` (no secret
  material) for uptime monitoring

### Phase 4 — Backward compatibility & rollout

The hard problem: old PC2 nodes (v1.2.7.x and earlier) call
`GET /api/ddrm/provision` and expect `usageKey` in the response. If we
remove `usageKey` immediately, every existing node breaks until they update.

**Two-step migration:**

- **Day 0 (this release lands)**: ship v1.2.8.0 with relayer support. Both
  supernodes serve **both** the legacy provision (still includes usageKey,
  re-issued post-rotation today) and the new relayer endpoint. Tier 0
  preferred on v1.2.8.0+ nodes; legacy tier path still works for older
  nodes.
- **Day 30**: launcher fleet on v1.2.8.0+ verified by telemetry (we
  already have the version-check ping from the update flow). Drop usageKey
  from provision response (envelope v2). Anyone still on ≤v1.2.7.x sees
  forced upgrade prompt.
- **Day 60**: optional — turn on Mode B (allowlist) for relayer if abuse
  signals appear in logs.

### What about Option B (per-node scoped keys)?

That's the better long-term answer but depends entirely on Chipotle-side
support. If Irzhy confirms per-API-key issuance is supported, schedule it as
a v1.3 task with this relayer as the bridge. The relayer + per-key scoping

### Why not just IP-allowlist `/api/ddrm/provision`?

Rejected — PC2 nodes run on residential IPs worldwide, no stable allowlist
exists. Auth must be cryptographic (the wallet) not network-layer.

### Why not put auth on the existing `/api/ddrm/provision`?

Considered (Option C in the original analysis). Rejected because:

- It still gives every node the same shared key — leak via any node compromise
  exposes the entire fleet
- Doesn't solve "key on the wire" — only "auth required to get key"
- The relayer architecture is roughly the same effort and is structurally
  better

### Existing infrastructure we leverage

- **SIWE pattern**: already implemented in
  `pc2-node/data/test-apps/elacity-market/wallet.js` `siweLogin()`
- **Wallet abstractions**: PC2 already has EOA + Smart Account wallets used
  by Elacity dApps; the same wallet signs the relayer challenge
- **Gateway proxying**: `deploy/web-gateway/index.js` already proxies HTTP
  traffic — adding a Chipotle relay endpoint follows the existing pattern
- **Ed25519 envelope code**: stays in place. Even though `usageKey` leaves
  the envelope, signing still protects integrity of the remaining config
  (apiUrl, pkpId, action CIDs)
